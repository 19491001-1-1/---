# 性能优化记录

本轮优化只改搜索层与解码层的实现方式，**不改变任何已有搜索结果**：相同种子、相同实例、相同算法，
优化前后的装载面积与放置列表逐位一致。全部 169 个测试与覆盖率门禁（行 80% / 分支 70%）保持通过。

> "行为不变"不是靠"同种子跑两遍一致"证明的——那只证明确定性，抓不住共享缓冲区别名这类
> **确定性错误**（错得一模一样）。真正的闸门是 `GoldenPinsTest`：把固定实例/种子下各算法的
> 精确面积与统计计数钉死，与优化前的数值对照（见 §六）。

---

## 一、方法：先测量，再决定改哪里

优化前先建基准，原因是"看起来该优化"的地方往往不是真瓶颈。事实证明这一步决定了整轮优化的方向。

基准设施位于 `src/jmh/java/`，由独立 Maven profile `bench` 承载，
默认 `./mvnw clean verify` **不编译、不运行**，因此测试数量与覆盖率门禁完全不受影响。

```bash
# 解码器吞吐（JMH）：Skyline / MaxRects / Guillotine × 3 个实例 × 定序/乱序
./mvnw -Pbench exec:exec -Djmh.args="-wi 3 -i 5 -w 1s -r 1s -f 1 -rf text \
  com.assessment.packing.bench.DecoderThroughputBenchmark"

# 搜索真正走的评价路径（JMH）：轻量评分 / 缓存命中 / 混合三档
./mvnw -Pbench exec:exec -Djmh.args="-wi 3 -i 5 -w 1s -r 1s -f 1 -rf text \
  com.assessment.packing.solver.EvaluationPathBenchmark"

# 六个搜索算法在固定评价预算下的求解耗时（JMH）
./mvnw -Pbench exec:exec -Djmh.args="-wi 3 -i 5 -w 1s -r 1s -f 1 -rf text \
  com.assessment.packing.bench.SearchEvaluationBenchmark"

# 解码耗时占搜索总耗时的比例 + 各算法缓存命中率（确定性探针，非 JMH）
./mvnw -Pbench exec:exec -Dexec.mainClass=com.assessment.packing.bench.DecodeShareProbe
```

> **为什么 `DecodeShareProbe` 不用 JMH**：JMH 在 `AverageTime` 模式下只报告实测耗时，
> 基准方法返回的派生比值会被直接忽略。最初用 JMH 写"解码占比"基准，输出的其实是总耗时本身，
> 数字看着合理但完全误导。派生比值改用确定性探针输出，可以逐项核对。

> **为什么 `EvaluationPathBenchmark` 放在 `solver` 包**：`DecodingCache` 是包私有的（只服务搜索内部），
> 要测它就只能在同一个包。基准包 `com.assessment.packing.bench` 里测不到这条真实路径——
> 这正是第一轮 `DecoderThroughputBenchmark` 的盲区（见 §4.1 口径提醒）。

环境：Temurin JDK 17.0.20.1（项目目标版本），`-wi 3 -i 5 -w 1s -r 1s -f 1`，Apple Silicon。

## 二、关键发现：真正的瓶颈不是重复解码

### 2.1 缓存命中率近乎为零

原计划的核心假设是"搜索过程中大量重复解码，统一缓存收益最大"。实测各算法在 gcut3 / gcut12
上跑满评价预算后的缓存命中率：

| 算法 | 解码次数 | 缓存命中 | 命中率 |
|---|---|---|---|
| Tabu（MOVE） | 15050 | 0 | **0.00%** |
| SA | 20000 | 0 | **0.00%** |
| ACO | 4046 | 5 | 0.12% |
| ILS | 13961 | 180 | 1.27% |
| GA | 8658 | 942 | 9.81% |
| AdaptiveGA | 11252 | 3763 | 25.06% |

Tabu/SA 的候选由 20~40 个零件的随机交换生成，两次生成同一个完整排列的概率可以忽略，
缓存对它们**永远不可能命中**。只有 AdaptiveGA 有实质命中率（约 25%）。

### 2.2 解码本身才是大头

`DecodeShareProbe` 测量"解码次数 × 单次解码耗时 ÷ 搜索总耗时"：

| 算法 | 实例 | 解码占比 |
|---|---|---|
| Tabu（MOVE） | gcut3 / gcut12 | 59.6% / 71.7% |
| SA | gcut3 / gcut12 | 73.1% / **85.8%** |
| ACO | gcut3 / gcut12 | 10.6% / 4.6% |
| ILS | gcut3 / gcut12 | 16.0% / 52.3% |
| GA | gcut3 / gcut12 | 25.7% / 24.4% |
| AdaptiveGA | gcut3 / gcut12 | 47.5% / 64.3% |

对 Tabu/SA 而言，解码占掉六到八成五的时间，而缓存一点忙都帮不上。
**结论：加速解码器本身，比缓存更有价值。**

### 2.3 剖析定位到具体一行

用 JFR（`settings=profile`）对 Skyline 解码循环采样，热点高度集中：

```
  88  SkylineSolver.solveInPriorityOrder  line: 68   ← 调用 chooseItem
  40  SkylineSolver.chooseItem            line: 111  ← 旋转分支评分
  37  SkylineSolver.chooseItem            line: 98   ← usedIds.contains(item.id())
```

`chooseItem` 是每次放置都对全部零件扫一遍的内层循环，其中
`Set<Integer> usedIds` 的 `contains(item.id())` 触发 `int` 装箱成 `Integer` 再算哈希。
这就是每次解码 3 µs 的主要构成。

## 三、实际做的改动

### 3.1 统一解码缓存（`DecodingCache`）

原先 Tabu/SA **完全没有缓存**；ACO/GA/ILS **各写了一份**私有 `SequenceKey` + 缓存，逻辑雷同、
容量语义还不一致（GA/ACO 存 `Long` 面积且无界，ILS 存整个 `Solution`）。现统一为一个包级私有类。

- **键**：`SequenceKey`（`int[]` + 预计算哈希），抽出三份重复实现。
- **值**：**只存装载面积 `long`，不存 `Solution`**。这点很关键：最初版本缓存整个 `Solution`，
  等于把携带完整放置列表的对象长期钉在缓存里，GA 反而从 75 ms 退化到 89 ms。改回存面积后消失。
  完整布局只在收尾解码一次（`DecodingCache.solve`），不走缓存。
- **有界**：LRU `LinkedHashMap`（`accessOrder=true`），默认容量 4096，避免长跑实验无界占用。
- **实例/解码器身份**：缓存实例在单次 `solve` 内构造，一个实例一个解码器，身份由生命周期承载，
  不需要塞进每个键。
- **不内置计数器、不做预算判定**：是否把命中计入评价数、预算耗尽如何退出，全部留在各算法原有
  循环里，从而各算法的评价计数口径与优化前逐位一致。

缓存的实际贡献有限（命中率见 2.1），但它消除了三份重复实现，并把"评价语义"统一到一个地方。

### 3.2 轻量评分接口（`PackingDecoder.packedAreaInPriorityOrder`）——8 个解码器全部实现

搜索阶段只需要一个分数，最终优胜排列才需要完整布局。接口 default 方法默认退化为完整解码后取面积。

**接口本身不产生收益，收益来自真正实现它。** 本轮把**全部 8 个解码器**都改为真正实现该方法（此前
只有 `SkylineSolver` 重写）。统一模式是：完整解码与轻量评分共用同一个
`run(instance, items, placements)`，当 `placements == null` 时只累计装入面积。

逐解码器的分档：

- **`placements` 是纯输出**（Guillotine、SkylineGlobal、Shelf、Shelf-Floor-Ceiling）：轻量路径直接传
  `null`，**完全不构造 `Placement`**，省掉整张放置列表。
- **`placements` 被当作状态读取**（BottomLeft、ContinuousBottomLeft 靠它做重叠/碰撞检测；MaxRects 的
  CP 启发式读它）：轻量路径仍构造列表（语义所需），但省掉 `Solution` 包装与 `packedArea` 求和。
  MaxRects 的非 CP 启发式不看它，直接传 `null`。
- **`MaxRectsBestSolver`**：内部五条启发式各完整跑一遍。轻量路径改为按轻量方式跑五条、只保留胜者。
- **适配器**（`PackingDecoders.adapter`）：另外 7 个底层求解器实现的是 `PackingAlgorithm`（只有
  `solve`），因此给每个底层求解器加了一个**包级私有**的 `packedAreaOf(Instance)`，适配器构造好有序
  `Instance` 后直接调它，避免 default 的"完整解码 + 构造 `Solution` + 再算面积"。

实验的 `DecoderMatrixRunner` 会遍历**全部 8 个解码器**跑搜索，因此这不只是理论收益。

因为两条路径走的是同一套放置逻辑（同一处 `chooseItem`、同一处 `replaceAfterPlacement` 等），
面积必然一致——这是"搜索轨迹不被优化改变"的前提，由 `DecodeEquivalenceTest` 的
`everyRealDecoderLightScoringMatchesFullDecode` 对**全部 8 个解码器 × 若干随机排列**逐个对照兜底
（见 §六）。

### 3.3 `Solution` 由 record 转为 final class

`packedArea()` 原本是每次调用都 stream 重算一遍放置列表，而它在 SA/ILS 的循环条件里被反复调用
（共 64 处调用点）。改为构造时算一次、存成字段。

### 3.4 消掉热路径装箱（本轮的**主要收益来源**）

`SkylineSolver`：

- `Set<Integer> usedIds` → 按零件编号索引的 `boolean[] used` + 计数。零件编号在实例内唯一，
  语义完全等价，消掉每次 `contains` 的装箱与哈希。
- 去掉每次改进都新建 `Choice` 对象，改为只维护"当前最优"的标量字段；哨兵取 `-1`
  （合法评分为 0~7，`-1` 专表"放不下"），并列时仍保持排列靠前的零件优先。
- 顺带删除已无调用者的 `score(…, Segment, …)` 重载。

这一项让 Skyline 解码 **快 1.24~1.39 倍**，直接带动六个搜索算法提速。

### 3.5 热循环去掉 `Map<Integer,Item>` 查表

`DecodingCache` 内部用 `Item[] byId` 按编号直接索引，替代原先每轮 `HashMap.get(id)`。
Tabu/SA/GA/ILS 里遗留的 `itemById` 映射与对应的 `decode`/`evaluate` 包装一并删除。

`DecodingCache.toItems`（把 `int[]` 排列还原成 `List<Item>`）进一步复用内部缓冲区：
构造时按实例零件数预分配一个 `ArrayList<Item> priority`，每次调用 `clear()` 后填入再返回，
不再每次 `new ArrayList<>(...)`。这个方法位于**评价热路径**上，每未命中一次调用一次，
原实现这笔分配随评价次数线性增长。

**为什么返回共享缓冲区是安全的**（已逐点核实）：

- 所有消费方都**只读取**该列表，从不修改。`SkylineSolver` 走 `boolean[] used` +
  自己的放置逻辑；`PackingDecoders.adapter` 把列表交给 `new Instance(...)`，
  而 `Instance` 的紧凑构造器里做了 `items = List.copyOf(items)`，**当场复制一份并持有副本**，
  不保留对缓冲区的引用。
- 没有任何解码器在 `solveInPriorityOrder` / `packedAreaInPriorityOrder` 之外持有它，
  也没有跨调用的生命周期依赖；下一次 `toItems` 覆盖内容时上一次的使用早已结束。
- 调用点集中在 `DecodingCache.areaOf` / `solve` 两处，都是"立即传给解码器、用完即弃"。

若将来新增解码器要保存或修改这个列表，必须改为返回副本（或在调用方传副本）。

### 3.6 实验级并行（默认关闭）

`ExperimentRunConfiguration` 新增白名单键 `parallelism`（默认 `1`，与串行行为逐位一致）。
`ExperimentRunner` 把三层循环展开成按串行顺序编号的任务清单，并行时结果写入**按下标寻址的数组**、
按 Future 顺序收集，因此并行产出的运行列表与串行**顺序和数值完全相同**。

- 每个任务自建求解器；`SolutionValidator` 无实例字段，可安全共享。
- 进度打印与断点写入都在调用线程按序进行，不交错。
- **时间预算实验（`TIME_MS`）强制串行**：并行会让算法争抢 CPU，耗时不再公平，
  配置层直接拒绝该组合并给出明确报错。
- 命令行入口通过环境变量开启：`PACKING_PARALLELISM=8 ./scripts/run-experiments.sh …`

### 3.7 第二轮补齐：单次查表、copy-on-accept、ACO 排列构造

第一轮之后又逐点复核，补掉几处"名义上有、实际没落地"的空间（见 §5 的判据）。

**（a）缓存单次查表。** `DecodingCache` 新增 `decodeAndStore`（不前置查表，直接解码回填）与复用键
`lookupKey`（`SequenceKey.set` 就地改写内容并同步哈希）。GA/ACO/ILS 的评价器原本是"先 `get`、
未命中再 `areaOf`"，未命中路径上会**构造两次 `SequenceKey`**（各自克隆数组 + 算哈希）。改用
`decodeAndStore` 后只剩一次查表。`get`/`contains` 也走复用键，不再每次新建键对象。

**（b）只在接受候选时复制（copy-on-accept）。** 这是第一轮之后**最大的一笔每评价分配**：

- Tabu 原本每个邻居都 `current.clone()` 整表；改为把候选写进复用的 `candidateScratch`，只有胜出
  的候选才 `Neighbor.owned()` 复制一份（`Neighbor` 会被长期持有并提升为 `currentSequence`，绝不能
  指向共享缓冲——所以是两阶段：扫描用 scratch，选中时复制）。`allSwaps` 也提到迭代循环外只建一次。
- SA 的 `randomSwapInto` 写入 scratch，**接受时**才 `clone()`；温度估计复用同一缓冲；`bestSequence`
  直接共享从不就地改写的 `currentSequence`（原实现多克隆了一次）。
- ILS 的评价器不再冗余克隆（调用方都在改动前先 `clone`）。

**（c）ACO 排列构造。** `constructPermutation` 里每个 `(位置,候选)` 对原本算两遍完全相同的
`alpha*log(pheromone) + beta*log(desirability)`（两轮扫描各一次），每个位置还新建一个
`double[itemCount]`。改为 `beta*log(desirability)` 整只蚂蚁算一次、每个位置的 `alpha*log(pheromone)`
两轮共用一份缓冲。`Math.log` 与乘法确定、加法操作数不变，故结果逐位不变。

三项都**不改变任何评价计数与搜索轨迹**：`SkylineAntColonyTest` 断言同种子的面积、布局、统计与
**收敛轨迹**全部一致；`HybridGeneticAlgorithmTest` 断言同种子的布局、统计与收敛过程一致。

**（d）MaxRects 热路径的容器分配（第三轮，JFR 剖析定位）。** JMH 只回答「MaxRects 比 Skyline 慢多少」，
回答不了慢在哪一段。用 JFR（`settings=profile`，60s，约 1000 万轮真实评价负载）对
`MaxRectsProfilingDriver light` 采样，结论是**分配而非算法**：

| 分配类 | 占比（改动前） |
|---|---|
| `ImmutableCollections$ListItr` | **47.0%** |
| `Object[]` | 18.2% |
| `FreeRectangle` | 10.8% |
| `ArrayList` | 4.6% |

第一大户 `ListItr` 不是数据，而是**遍历不可变列表的迭代器**：`pruneFreeList` 结尾 `List.copyOf(result)`
产出不可变列表，随后 `findBestCandidate` 的 `for (FreeRectangle free : freeRectangles)` 每调用一次
就新建一个迭代器——而它是**每轮、每个剩余零件**都要跑的循环。`Object[]` 18.2% 是 `List.copyOf`
的整表复制，`ArrayList` 4.6% 是 `run()` 每轮 `new ArrayList<>()` 与扩容。三处同源。

改法是让容器在整次求解里恒定：

- `run()` 用两块列表缓冲轮换（当前 / 切割结果），每轮只清空重填；
- 内部新增 `splitFreeRectanglesInto`、`pruneFreeListInPlace` 就地改写，不新建列表也不新建数组；
- 热循环改下标遍历，消除迭代器。

CPU 采样里 `score()` 独占 44.6%，但那是**设计使然**——`MaxRectsBestSolver` 依次跑完五种启发式再取最优，
本身就是五倍计算量（4.1 节已注明）。因此本轮只清理它周围的分配，不动评分公式。

**等价性**：480 个配置组合（120 个 gcut 实例 × 5 启发式 × 全局/顺序选择 × 旋转开关 × 2 种排序）
的完整布局（实例名、启发式、模式、每个 placement 的零件号与 x/y/rotated）**逐位对拍一致**。
剪枝的判定顺序逐字保持原样（外层 `i` 升序、内层 `j` 从 `i+1` 起，先判 `i` 含 `j`、再判 `j` 含 `i`），
输出保留项仍按原下标升序，因此元素与次序不变——`MaxRectsGeometryTest` 直接比对这一点。

**结果**：轻量评分路径（搜索真正走的路径）60 秒内轮次 5,526,269 → **8,733,887**，**提速 1.58x**；
JFR 复扫确认每次评价的分配量 12.9 kB → **4.7 kB，降 63.6%**，`ListItr` 从 47.0% 降到 0。

> 与 ACO 一样，这轮再次说明：**先用剖析定位，再动手**。MaxRects 看起来"只是慢"，
> 实际慢在三个可以用同一套缓冲消掉的容器分配上，而不是自由矩形算法的固有复杂度。

## 四、前后对照

### 4.1 解码器吞吐（µs/op，越小越好）

| 用例 | 解码器 | 实例 | 优化前 | 优化后 | 倍数 |
|---|---|---|---|---|---|
| 定序 | SKYLINE | gcut1 | 1.46 | 1.32 | 1.10x |
| 定序 | SKYLINE | gcut3 | 3.05 | 2.47 | **1.24x** |
| 定序 | SKYLINE | gcut12 | 3.28 | 2.72 | **1.21x** |
| 乱序 | SKYLINE | gcut3 | 5.24 | 4.16 | **1.26x** |
| 乱序 | SKYLINE | gcut12 | 6.29 | 4.79 | **1.31x** |

MAXRECTS 与 GUILLOTINE 本轮未改内部实现，重跑落在 **0.88x~1.18x**，全部在测量噪声内
（±5% 上下），符合"未改动"的预期。

Skyline 是六个搜索算法的默认解码器，也是唯一改了内部实现的解码器，提速最明显。

> **基准口径提醒**：`DecoderThroughputBenchmark` 直接调用 `solveInPriorityOrder`（完整解码 +
> 构造 `Solution`/`Placement`），**绕过 `DecodingCache` 与轻量评分**，因此它**不覆盖**搜索真正走的
> 路径。`EvaluationPathBenchmark`（新增，`solver` 包内，因为 `DecodingCache` 是包私有）专门补齐这块
> 盲区：把"轻量评分（未命中）"、"缓存命中查表"、"未命中+命中混合"三档分开测量，见下表。

> MaxRects 单次成本高（8~11 µs）是**设计使然**：`MaxRectsBestSolver` 依次跑全部五种启发式
> 再取最优，用约五倍计算量换取对启发式选择的稳健性。这不是待消除的低效。

### 4.1b 搜索评价路径（µs/op，越小越好）

`EvaluationPathBenchmark`（新增）把搜索真正走的路径拆成三档。同一口径
（`-wi 3 -i 5 -w 1s -r 1s -f 1`，Temurin 17.0.20.1）实测（µs/op）：

| 解码器 | 实例 | `lightScoreUncached` | `cachedAreaLookup` | `cachedAreaShuffled` |
|---|---|---|---|---|
| SKYLINE | gcut1 | 1.31 | **0.020** | 2.55 |
| SKYLINE | gcut3 | 2.13 | **0.038** | 4.78 |
| SKYLINE | gcut12 | 2.20 | **0.066** | 5.80 |
| MAXRECTS | gcut1 | 3.79 | **0.020** | 6.46 |
| MAXRECTS | gcut3 | 7.35 | **0.038** | 15.76 |

### 4.2d 缓存策略对照：该不该开缓存，由命中率回答

解码缓存要付出算哈希、查表、存条目、占内存的固定成本，只有命中率足够高才回本。
用确定性探针（`CacheStrategyProbe`，同一次 JVM 内切换三种策略以保证面对同一套 JIT 与堆状态，
每个策略测量前先丢弃两次运行）对照：**无缓存**（`PACKING_CACHE_CAPACITY=0`）、
**固定 4096**（默认）、**固定 64**。中位耗时 ms，固定 4096 列括号内为命中率：

| 算法 | 实例 | 固定 4096 | 无缓存 | 固定 64 | 命中率(4096) | 结论 |
|---|---|---|---|---|---|---|
| Tabu（MOVE） | gcut3 | 57.50 | **44.91** | 42.31 | 0.35% | 纯开销 |
| Tabu（MOVE） | gcut12 | 44.99 | **43.06** | 45.78 | 0.10% | 纯开销 |
| SA | gcut3 | 68.93 | **64.48** | 66.71 | 0.40% | 纯开销 |
| SA | gcut12 | 77.33 | **72.10** | 69.93 | 0.16% | 纯开销 |
| ACO | gcut3 | 63.95 | 63.45 | **63.22** | 0.12% | 纯开销 |
| ACO | gcut12 | 173.93 | **158.31** | 159.20 | 0.00% | 纯开销 |
| ILS | gcut3 | 47.78 | **44.36** | 46.55 | 1.27% | 纯开销 |
| ILS | gcut12 | 77.54 | **70.53** | 70.91 | 0.82% | 纯开销 |
| GA | gcut3 | 51.35 | **47.80** | 47.61 | 9.81% | 中性 |
| GA | gcut12 | 58.91 | 58.92 | 60.07 | 8.69% | 中性 |
| AdaptiveGA | gcut3 | 61.05 | 62.49 | 61.29 | 25.06% | 略优 |
| AdaptiveGA | gcut12 | **42.78** | 48.04 | 47.39 | 25.57% | **确有收益（1.12x）** |

**三种策略的装载面积逐位相同**（上表 12 行 × 3 策略的面积全部一致），证明缓存只是记忆层，
只能减少解码次数，绝不改变搜索结果——这正是 3.1 把开关做进 `DecodingCache` 而非各算法内部的价值。

按命中率分三档，规律很干净：

- **命中率 ≤ 1.3%（Tabu/SA/ACO/ILS）——缓存是净开销。** 这四个算法的候选生成方式产生的排列几乎不重复：
  Tabu 每次移动换一对零件，SA 每次交换都换随机对，ACO 每只蚂蚁从零构造。查表、存条目的固定成本
  收不回来，无缓存反而快 5%~10%。**默认容量按 4096 给是历史遗留，对这四类算法偏高。**
- **命中率 ~9%（GA）——中性。** 交叉产生的子代开始出现重复，命中收益与开销大致抵消。
- **命中率 ~25%（AdaptiveGA）——确有收益。** 它会在搜索中反复回访少数几个精英排列，重复度高，
  gcut12 上 42.78 对 48.04，快 12%。

> 但**不建议按算法下调默认容量**：默认值只在未显式配置时生效，而搜索层各算法共用同一份
> `DecodingCacheCapacity.configured()`；按算法分支配置会把一处简单开关变成一张需要维护的映射表，
> 而收益只有个位数百分比。这个「该不该开」的数据留给实验者：需要极致吞吐时设
> `PACKING_CACHE_CAPACITY=0`，需要复现旧行为时保持默认。

## 五、明确**没有**做的优化（以及理由）

### 5.1 增量评价（重用相邻排列的共同前缀）——不做

原计划把它列为待考察项，条件是"解码占搜索时间比例高"。数据是分裂的：

- **不支持**：解码在 ACO 只占 4.6%~10.6%，而在这些算法里最常用的候选生成方式
  （GA 交叉、ACO 构造排列）根本不产生"共同前缀"，Skyline 的天际线结构也难以高效快照/回滚。
- **支持**：Tabu/SA 局部交换产生的排列**确实**共享长前缀，且解码占其耗时 60~86%，理论上空间很大。

但没有做，原因有三：

1. 需要逐解码器实现状态快照/回滚（Skyline 的 `TreeMap`+堆、MaxRects 的自由矩形集、Guillotine 的
   剩余矩形，结构各不相同），复杂度和回归风险远高于本轮其他改动。
2. 收益与解码器强耦合，只对 Skyline 有明确空间，换一个解码器就白做。
3. 本轮已经用**低得多的代价**拿到了 1.2–1.5x（3.4 节消装箱）。在这个基础上，
   增量评价的边际收益不足以支撑其风险。

如果后续要进一步压榨 Tabu/SA，这是唯一有实质空间的方向，建议单独立项并逐个解码器配等价性测试。

### 5.2 其余热路径复制——已随缓存重构与 copy-on-accept 消除

原计划阶段 D 的"排列状态统一 `int[]`、减少 `Item` 列表重建、`Item[] byId` 查表"，
大部分已随 3.5 节统一缓存完成；**"减少 `Item` 列表重建"** 由 `toItems` 复用内部缓冲区补齐、
**"只在接受候选时复制"** 由 3.7(b) 的 copy-on-accept 补齐。至此评价热路径上不再有
"每个候选一次整表分配"：候选写进共享 scratch，只有胜出的候选才复制。

剩余的 `int[] clone()` 都是必要的：要么是缓存键、要么是接受候选时的一次复制、
要么是 ILS 里"改动前先克隆"的所有权准备，都**不在每评价一次**的路径上。

### 5.3 `PackingDecoders.adapter` 复用原始实例——无收益，不做

原计划想消掉适配器里每次解码的 `new Instance(...)`。核查后发现它是**每解码一次的固定成本**，
不是每次候选的增量成本；且改成复用原始实例会**改变语义**（多数适配器的内部求解器按自己配置的
`ItemOrder` 重新排序，直接传入有序列表会让 `AREA_DESC` 等排序失效），风险大于收益。保留原样。

> 附带好处：`Instance` 构造器里的 `List.copyOf` 是 3.5 节 `toItems` 复用缓冲区得以安全的原因之一
> ——适配器当场复制，不保留对共享缓冲区的引用。删除这里的 `Instance` 会同时破坏这条安全性。

## 六、回归与等价性保障

| 测试 | 作用 |
|---|---|
| `DecodingCacheTest`（新增） | 命中/未命中、LRU 有界淘汰、`put`/`contains`、`decodeAndStore` 不重复查表、复用键不复活已淘汰条目、跨实例与跨解码器不串味 |
| `DecodeEquivalenceTest`（新增） | 对抗性解码器下缓存面积与全新解码逐个对照；六个搜索算法同种子两遍结果逐位一致。**全部 8 个真实解码器的轻量评分由 `everyRealDecoderLightScoringMatchesFullDecode` 兜底**：对每个解码器 × 若干随机排列断言 `packedAreaInPriorityOrder == solveInPriorityOrder().packedArea()` |
| `GoldenPinsTest`（新增） | **行为不变的硬闸门**：Tabu 六模式（gcut5）、SA（gcut2）、混合GA（gcut2）的精确面积与统计计数全部钉死。"同种子跑两遍一致"抓不住共享缓冲区别名这类**确定性错误**，只有与优化前的精确数值对照才行 |
| `ExperimentParallelismTest`（新增） | 并行与串行的运行列表顺序、面积、布局、评价数逐项相等；`runs.csv` 剔除全部耗时列（`elapsed_ms` 及 MaxRects 的 `bssf_ms` 等）后逐字节一致；时间预算 + 并行被拒绝 |
| `ExperimentInfrastructureTest`（扩展） | `parallelism` 合法值接受、与 `maxMilliseconds` 组合被拒绝、非正值被拒绝 |
| `ExperimentParallelismGuardTest`（新增） | 并行度上限（`MAX_PARALLELISM`）越界被拒、上限本身被接受；**断点续跑**场景下并行与串行的 `runs.csv` 除耗时列外逐字节一致 |
| `CacheStrategyEquivalenceTest`（新增） | 三种缓存策略（无缓存 / 固定 / 小容量）下 Tabu、SA、ILS、ACO 的布局、面积与**总评价次数**（解码 + 命中）逐位一致；GA/ACO 等"命中免费"族的评价计数口径差异被显式钉住 |
| `DecodingCacheCapacityTest`（新增） | `PACKING_CACHE_CAPACITY` 的解析：默认值、显式值（含 0 即关闭）、空白视为未设置、拒绝负数与非整数 |
| `SkylineTabuSearchTest` / `SkylineSimulatedAnnealingTest` | 各自保留同种子可复现与合法性用例；精确数值集中在 `GoldenPinsTest` |
| `PackingDecoderIntegrationTest`(56) / `AlgorithmCatalogTest` / `QualityBaselineTest` | 全部保持通过 |

`DecodeEquivalenceTest` 在开发过程中**实际拦下过一次回归**：把 `SkylineSolver` 的
"当前最优评分"哨兵从 `Integer.MIN_VALUE` 改成 `-1` 之前，不可放的零件（评分为 `-1`）
会被误当成合法候选，产生越界布局，被该测试与 `AllAlgorithmsRobustnessTest` 同时抓到。
