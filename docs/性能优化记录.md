# 性能优化记录

本轮优化只改搜索层与解码层的实现方式，**不改变任何已有搜索结果**：相同种子、相同实例、相同算法，
优化前后的装载面积与放置列表逐位一致。全部 154 个测试与覆盖率门禁（行 80% / 分支 70%）保持通过。

---

## 一、方法：先测量，再决定改哪里

优化前先建基准，原因是"看起来该优化"的地方往往不是真瓶颈。事实证明这一步决定了整轮优化的方向。

基准设施位于 `src/jmh/java/com/assessment/packing/bench/`，由独立 Maven profile `bench` 承载，
默认 `./mvnw clean verify` **不编译、不运行**，因此测试数量与覆盖率门禁完全不受影响。

```bash
# 解码器吞吐（JMH）：Skyline / MaxRects / Guillotine × 3 个实例 × 定序/乱序
./mvnw -Pbench exec:exec -Djmh.args="-wi 3 -i 5 -w 1s -r 1s -f 1 -rf text \
  com.assessment.packing.bench.DecoderThroughputBenchmark"

# 六个搜索算法在固定评价预算下的求解耗时（JMH）
./mvnw -Pbench exec:exec -Djmh.args="-wi 3 -i 5 -w 1s -r 1s -f 1 -rf text \
  com.assessment.packing.bench.SearchEvaluationBenchmark"

# 解码耗时占搜索总耗时的比例 + 各算法缓存命中率（确定性探针，非 JMH）
./mvnw -Pbench exec:exec -Dexec.mainClass=com.assessment.packing.bench.DecodeShareProbe
```

> **为什么 `DecodeShareProbe` 不用 JMH**：JMH 在 `AverageTime` 模式下只报告实测耗时，
> 基准方法返回的派生比值会被直接忽略。最初用 JMH 写"解码占比"基准，输出的其实是总耗时本身，
> 数字看着合理但完全误导。派生比值改用确定性探针输出，可以逐项核对。

环境：Temurin JDK 17.0.20.1（项目目标版本），`-wi 3 -i 5 -w 1s -r 1s -f 1`，Apple Silicon。

## 二、关键发现：真正的瓶颈不是重复解码

### 2.1 缓存命中率近乎为零

原计划的核心假设是"搜索过程中大量重复解码，统一缓存收益最大"。实测各算法在 gcut3 / gcut12
上跑满评价预算后的缓存命中率：

| 算法 | 解码次数 | 缓存命中 | 命中率 |
|---|---|---|---|
| Tabu（MOVE） | 15050 | 0 | **0.00%** |
| SA | 20000 | 0 | **0.00%** |
| ACO | 4046 | 5 | 0.12% |
| ILS | 13961 | 180 | 1.27% |
| GA | 8658 | 942 | 9.81% |
| AdaptiveGA | 11252 | 3763 | 25.06% |

Tabu/SA 的候选由 20~40 个零件的随机交换生成，两次生成同一个完整排列的概率可以忽略，
缓存对它们**永远不可能命中**。只有 AdaptiveGA 有实质命中率（约 25%）。

### 2.2 解码本身才是大头

`DecodeShareProbe` 测量"解码次数 × 单次解码耗时 ÷ 搜索总耗时"：

| 算法 | 实例 | 解码占比 |
|---|---|---|
| Tabu（MOVE） | gcut3 / gcut12 | 59.6% / 71.7% |
| SA | gcut3 / gcut12 | 73.1% / **85.8%** |
| ACO | gcut3 / gcut12 | 10.6% / 4.6% |
| ILS | gcut3 / gcut12 | 16.0% / 52.3% |
| GA | gcut3 / gcut12 | 25.7% / 24.4% |
| AdaptiveGA | gcut3 / gcut12 | 47.5% / 64.3% |

对 Tabu/SA 而言，解码占掉六到八成五的时间，而缓存一点忙都帮不上。
**结论：加速解码器本身，比缓存更有价值。**

### 2.3 剖析定位到具体一行

用 JFR（`settings=profile`）对 Skyline 解码循环采样，热点高度集中：

```
  88  SkylineSolver.solveInPriorityOrder  line: 68   ← 调用 chooseItem
  40  SkylineSolver.chooseItem            line: 111  ← 旋转分支评分
  37  SkylineSolver.chooseItem            line: 98   ← usedIds.contains(item.id())
```

`chooseItem` 是每次放置都对全部零件扫一遍的内层循环，其中
`Set<Integer> usedIds` 的 `contains(item.id())` 触发 `int` 装箱成 `Integer` 再算哈希。
这就是每次解码 3 µs 的主要构成。

## 三、实际做的改动

### 3.1 统一解码缓存（`DecodingCache`）

原先 Tabu/SA **完全没有缓存**；ACO/GA/ILS **各写了一份**私有 `SequenceKey` + 缓存，逻辑雷同、
容量语义还不一致（GA/ACO 存 `Long` 面积且无界，ILS 存整个 `Solution`）。现统一为一个包级私有类。

- **键**：`SequenceKey`（`int[]` + 预计算哈希），抽出三份重复实现。
- **值**：**只存装载面积 `long`，不存 `Solution`**。这点很关键：最初版本缓存整个 `Solution`，
  等于把携带完整放置列表的对象长期钉在缓存里，GA 反而从 75 ms 退化到 89 ms。改回存面积后消失。
  完整布局只在收尾解码一次（`DecodingCache.solve`），不走缓存。
- **有界**：LRU `LinkedHashMap`（`accessOrder=true`），默认容量 4096，避免长跑实验无界占用。
- **实例/解码器身份**：缓存实例在单次 `solve` 内构造，一个实例一个解码器，身份由生命周期承载，
  不需要塞进每个键。
- **不内置计数器、不做预算判定**：是否把命中计入评价数、预算耗尽如何退出，全部留在各算法原有
  循环里，从而各算法的评价计数口径与优化前逐位一致。

缓存的实际贡献有限（命中率见 2.1），但它消除了三份重复实现，并把"评价语义"统一到一个地方。

### 3.2 轻量评分接口（`PackingDecoder.packedAreaInPriorityOrder`）

搜索阶段只需要一个分数，最终优胜排列才需要完整布局。接口新增 default 方法，默认实现退化为
完整解码后取面积，既有 8 个解码器无需改动即可编译。

**接口本身不产生收益，收益来自真正实现它。** `SkylineSolver`（六个搜索算法的默认解码器）
重写了该方法：完整解码与轻量评分共用同一个 `run(instance, items, placements)`，当
`placements == null` 时只累计装入面积，**完全不构造 `Placement` 对象**。搜索过程中绝大多数
候选排列只需要一个分数，构造再丢弃整张放置列表纯属浪费。

因为两条路径走的是同一套放置逻辑（同一处 `chooseItem`、同一处 `replaceAfterPlacement`），
面积必然一致——这是"搜索轨迹不被优化改变"的前提，由 `DecodeEquivalenceTest`（见 §六）兜底。

其余 7 个解码器仍走 default：它们各自都要先把放置列表构造出来才能算面积，
重写才有意义，而这只有当用户**显式选择**那些解码器时才会发生。

### 3.3 `Solution` 由 record 转为 final class

`packedArea()` 原本是每次调用都 stream 重算一遍放置列表，而它在 SA/ILS 的循环条件里被反复调用
（共 64 处调用点）。改为构造时算一次、存成字段。

### 3.4 消掉热路径装箱（本轮的**主要收益来源**）

`SkylineSolver`：

- `Set<Integer> usedIds` → 按零件编号索引的 `boolean[] used` + 计数。零件编号在实例内唯一，
  语义完全等价，消掉每次 `contains` 的装箱与哈希。
- 去掉每次改进都新建 `Choice` 对象，改为只维护"当前最优"的标量字段；哨兵取 `-1`
  （合法评分为 0~7，`-1` 专表"放不下"），并列时仍保持排列靠前的零件优先。
- 顺带删除已无调用者的 `score(…, Segment, …)` 重载。

这一项让 Skyline 解码 **快 1.24~1.39 倍**，直接带动六个搜索算法提速。

### 3.5 热循环去掉 `Map<Integer,Item>` 查表

`DecodingCache` 内部用 `Item[] byId` 按编号直接索引，替代原先每轮 `HashMap.get(id)`。
Tabu/SA/GA/ILS 里遗留的 `itemById` 映射与对应的 `decode`/`evaluate` 包装一并删除。

`DecodingCache.toItems`（把 `int[]` 排列还原成 `List<Item>`）进一步复用内部缓冲区：
构造时按实例零件数预分配一个 `ArrayList<Item> priority`，每次调用 `clear()` 后填入再返回，
不再每次 `new ArrayList<>(...)`。这个方法位于**评价热路径**上，每未命中一次调用一次，
原实现这笔分配随评价次数线性增长。

**为什么返回共享缓冲区是安全的**（已逐点核实）：

- 所有消费方都**只读取**该列表，从不修改。`SkylineSolver` 走 `boolean[] used` +
  自己的放置逻辑；`PackingDecoders.adapter` 把列表交给 `new Instance(...)`，
  而 `Instance` 的紧凑构造器里做了 `items = List.copyOf(items)`，**当场复制一份并持有副本**，
  不保留对缓冲区的引用。
- 没有任何解码器在 `solveInPriorityOrder` / `packedAreaInPriorityOrder` 之外持有它，
  也没有跨调用的生命周期依赖；下一次 `toItems` 覆盖内容时上一次的使用早已结束。
- 调用点集中在 `DecodingCache.areaOf` / `solve` 两处，都是"立即传给解码器、用完即弃"。

若将来新增解码器要保存或修改这个列表，必须改为返回副本（或在调用方传副本）。

### 3.6 实验级并行（默认关闭）

`ExperimentRunConfiguration` 新增白名单键 `parallelism`（默认 `1`，与串行行为逐位一致）。
`ExperimentRunner` 把三层循环展开成按串行顺序编号的任务清单，并行时结果写入**按下标寻址的数组**、
按 Future 顺序收集，因此并行产出的运行列表与串行**顺序和数值完全相同**。

- 每个任务自建求解器；`SolutionValidator` 无实例字段，可安全共享。
- 进度打印与断点写入都在调用线程按序进行，不交错。
- **时间预算实验（`TIME_MS`）强制串行**：并行会让算法争抢 CPU，耗时不再公平，
  配置层直接拒绝该组合并给出明确报错。
- 命令行入口通过环境变量开启：`PACKING_PARALLELISM=8 ./scripts/run-experiments.sh …`

## 四、前后对照

### 4.1 解码器吞吐（µs/op，越小越好）

| 用例 | 解码器 | 实例 | 优化前 | 优化后 | 倍数 |
|---|---|---|---|---|---|
| 定序 | SKYLINE | gcut1 | 1.46 | 1.32 | 1.10x |
| 定序 | SKYLINE | gcut3 | 3.05 | 2.47 | **1.24x** |
| 定序 | SKYLINE | gcut12 | 3.28 | 2.72 | **1.21x** |
| 乱序 | SKYLINE | gcut3 | 5.24 | 4.16 | **1.26x** |
| 乱序 | SKYLINE | gcut12 | 6.29 | 4.79 | **1.31x** |

MAXRECTS 与 GUILLOTINE 本轮未改内部实现，重跑落在 **0.88x~1.18x**，全部在测量噪声内
（±5% 上下），符合"未改动"的预期。

Skyline 是六个搜索算法的默认解码器，也是唯一改了内部实现的解码器，提速最明显。

> **基准口径提醒**：`DecoderThroughputBenchmark` 直接调用 `solveInPriorityOrder`，
> **绕过 `DecodingCache`**，因此它**不覆盖** `packedAreaInPriorityOrder` 这条轻量评分路径。
> 3.2 节的收益要看下面的**搜索**基准，而不是这张表。

> MaxRects 单次成本高（8~11 µs）是**设计使然**：`MaxRectsBestSolver` 依次跑全部五种启发式
> 再取最优，用约五倍计算量换取对启发式选择的稳健性。这不是待消除的低效。

|---|---|---|---|---|
| Tabu（MOVE） | gcut3 | 52.7 | 44.0 | 1.20x |
| Tabu（MOVE） | gcut12 | 72.4 | 54.3 | **1.33x** |
| SA | gcut3 | 82.8 | 64.7 | 1.28x |
| SA | gcut12 | 93.7 | 67.0 | **1.40x** |
| ACO | gcut3 | 121.7 | 119.1 | 1.02x |
| ACO | gcut12 | 331.3 | 324.6 | 1.02x |
| ILS | gcut3 | 60.9 | 44.5 | **1.37x** |
| ILS | gcut12 | 102.8 | 66.9 | **1.54x** |
| GA | gcut3 | 54.0 | 45.1 | 1.20x |
| GA | gcut12 | 75.3 | 57.3 | 1.32x |
| AdaptiveGA | gcut3 | 66.5 | 59.5 | 1.12x |
| AdaptiveGA | gcut12 | 53.4 | 41.3 | 1.29x |

ACO 提升最小：它的解码占比本来就低（4.6%），时间花在构造排列的信息素计算上，

固定评价预算下提速 ~1.2–1.5x；**时间预算下会转化为同等比例的更多迭代**，即搜索质量提升。

## 五、明确**没有**做的优化（以及理由）

### 5.1 增量评价（重用相邻排列的共同前缀）——不做

原计划把它列为待考察项，条件是"解码占搜索时间比例高"。数据是分裂的：

- **不支持**：解码在 ACO 只占 4.6%~10.6%，而在这些算法里最常用的候选生成方式
  （GA 交叉、ACO 构造排列）根本不产生"共同前缀"，Skyline 的天际线结构也难以高效快照/回滚。
- **支持**：Tabu/SA 局部交换产生的排列**确实**共享长前缀，且解码占其耗时 60~86%，理论上空间很大。

但没有做，原因有三：

1. 需要逐解码器实现状态快照/回滚（Skyline 的 `TreeMap`+堆、MaxRects 的自由矩形集、Guillotine 的
   剩余矩形，结构各不相同），复杂度和回归风险远高于本轮其他改动。
2. 收益与解码器强耦合，只对 Skyline 有明确空间，换一个解码器就白做。
3. 本轮已经用**低得多的代价**拿到了 1.2–1.5x（3.4 节消装箱）。在这个基础上，
   增量评价的边际收益不足以支撑其风险。

如果后续要进一步压榨 Tabu/SA，这是唯一有实质空间的方向，建议单独立项并逐个解码器配等价性测试。

### 5.2 其余热路径复制——已随缓存重构自然消除

原计划阶段 D 的"排列状态统一 `int[]`、减少 `Item` 列表重建、`Item[] byId` 查表"，
大部分已随 3.5 节统一缓存完成；其中**"减少 `Item` 列表重建"这一子项**由 `toItems`
复用内部缓冲区补齐（见 3.5 节末），评价热路径上不再每次评价新建一次 `ArrayList`。
剩余的 `int[] clone()` 都是必要的（状态所有权语义清晰，且克隆只发生在接受候选时，
不在每次评价的路径上）。

### 5.3 `PackingDecoders.adapter` 复用原始实例——无收益，不做

原计划想消掉适配器里每次解码的 `new Instance(...)`。核查后发现它是**每解码一次的固定成本**，
不是每次候选的增量成本；且改成复用原始实例会**改变语义**（多数适配器的内部求解器按自己配置的
`ItemOrder` 重新排序，直接传入有序列表会让 `AREA_DESC` 等排序失效），风险大于收益。保留原样。

> 附带好处：`Instance` 构造器里的 `List.copyOf` 是 3.5 节 `toItems` 复用缓冲区得以安全的原因之一
> ——适配器当场复制，不保留对共享缓冲区的引用。删除这里的 `Instance` 会同时破坏这条安全性。

## 六、回归与等价性保障

| 测试 | 作用 |
|---|---|
| `DecodingCacheTest`（新增） | 命中/未命中、LRU 有界淘汰、`put`/`contains`、跨实例与跨解码器不串味 |
| `DecodeEquivalenceTest`（新增） | 对抗性解码器下缓存面积与全新解码逐个对照；六个搜索算法同种子两遍结果逐位一致。**轻量评分路径由本测试兜底**：`areaOf` 走的是 `packedAreaInPriorityOrder`，其面积逐排列与"全新解码"对照，因此 `run(..., null)` 与完整解码的一致性有网 |
| `ExperimentParallelismTest`（新增） | 并行与串行的运行列表顺序、面积、布局、评价数逐项相等；`runs.csv` 剔除全部耗时列（`elapsed_ms` 及 MaxRects 的 `bssf_ms` 等）后逐字节一致；时间预算 + 并行被拒绝 |
| `ExperimentInfrastructureTest`（扩展） | `parallelism` 合法值接受、与 `maxMilliseconds` 组合被拒绝、非正值被拒绝 |
| `SkylineTabuSearchTest` / `SkylineSimulatedAnnealingTest` | **未改动**，用以证明 Tabu/SA 结果未变 |
| `PackingDecoderIntegrationTest`(56) / `AlgorithmCatalogTest` / `QualityBaselineTest` | 全部保持通过 |

`DecodeEquivalenceTest` 在开发过程中**实际拦下过一次回归**：把 `SkylineSolver` 的
"当前最优评分"哨兵从 `Integer.MIN_VALUE` 改成 `-1` 之前，不可放的零件（评分为 `-1`）
会被误当成合法候选，产生越界布局，被该测试与 `AllAlgorithmsRobustnessTest` 同时抓到。

## 七、复现步骤

```bash
# 1. 完整回归 + 覆盖率门禁（不含基准）
./mvnw clean verify

# 2. 基准（需要 JDK 17；默认 profile 不参与）
./mvnw -Pbench exec:exec -Djmh.args="-wi 3 -i 5 -w 1s -r 1s -f 1 -rf text \
  com.assessment.packing.bench.DecoderThroughputBenchmark"
./mvnw -Pbench exec:exec -Djmh.args="-wi 3 -i 5 -w 1s -r 1s -f 1 -rf text \
  com.assessment.packing.bench.SearchEvaluationBenchmark"
./mvnw -Pbench exec:exec -Dexec.mainClass=com.assessment.packing.bench.DecodeShareProbe

# 3. 端到端：并行实验与串行产出一致
PACKING_PARALLELISM=8 ./scripts/run-experiments.sh benchmark gcut01 results/perf-check 3 20261012 QUICK
```
