# 代码结构与求解流程

算法实现集中在 `solver/`。`experiment/`组织配置、独立运行与统计，`validation/`检查输出是否合法。`web/`与`frontend/`用于交互查看和实验记录管理，算法与命令行运行不依赖前端。

算法目录以 `AlgorithmCatalog.families()` 为统一家族配置模型，通过 `GET /api/algorithms/families` 提供给前端。评分、取件、WM 与禁忌记忆均作为配置差异说明，五个非 NF 的 Shelf-WM 配置带 `compatibilityOnly` 标记并默认收起；旧标识和既有接口继续可读。完整遍历覆盖全部配置。

Web 实验报告额外传入带解码器身份的 `ConfigurationRun`，按实例、搜索器、解码器聚合合法运行后选冠军。`instance-winners.csv` 的 Web 格式包含 `decoder` 列，普通 CLI 实验格式维持既有固定解码器格式；双方均保留并列冠军与合法运行计数。

## 设计目标

系统将问题模型、求解器、结果验证与实验统计分离，使各算法可以共享数据读取、配置、合法性检查和报告生成流程。

## 模块职责

```text
InstanceReader
      │
      ▼
Instance / Item
      │
      ▼
PackingAlgorithm ◄─ SolverFactory / AlgorithmCatalog
      ▲
      │  搜索算法注入
PackingDecoder ◄─ Shelf / Floor-Ceiling / Bottom-Left / Skyline / MaxRects / Guillotine
      │
      ▼
Solution / Placement
      ├── SolutionValidator
      └── ExperimentRunner ──► CSV / SVG / HTML
```

Web接口作为可视化适配层调用上述算法核心：

```text
HTTP / JSON
    │
    ▼
Controller ──► Web DTO ──► Catalog / Instance / Solve Service
                                      │
                                      ▼
                         SolverFactory + SolutionValidator
```

Web DTO 不暴露求解器实例、内部配置对象或文件路径。实例 ID 先从后端配置的目录中建立白名单，
求解请求只能引用其中的稳定 ID。

### Maven 结构决策

当前保持单 Maven 模块。算法核心、CLI、实验脚本与 Web 适配层共用同一份编译产物，
可避免为了新增 API 而移动已经被固定种子和 46 个入口回归测试覆盖的源码。Maven 同时产出：

- 以 `Main` 为主类的普通 CLI JAR；
- 以 `PackingWebApplication` 为主类、分类名为 `web` 的 Spring Boot 可执行 JAR。

前端使用根目录 `frontend/` 独立管理，不把 Node 构建链混入算法核心的 Maven 编译路径。

#### 前端打包与部署形态

默认构建（`./mvnw clean verify`）**不触碰 Node**，前端独立构建、独立部署，Vite 开发服务器把
`/api` 代理到后端。需要自带前端的可执行包时显式启用 `frontend` profile：

```bash
./mvnw -Pfrontend package
```

该 profile 用 `frontend-maven-plugin` 把固定版本的 Node 与 pnpm 下载到 `target/`，复用
`frontend/package.json` 已有的脚本执行类型检查与 `vite build`，再把 `frontend/dist` 复制进
`target/classes/static`，由 Spring Boot 作为 classpath 静态资源托管。**构建机不需要预装 Node**，
本机与 CI 走同一条路径。用 profile 而不是让默认构建带上前端，是为了让只想跑后端测试的场景
不必被迫具备 Node 工具链——「交付单 jar」是一个显式动作。

**单 jar 形态附带一个 SPA 回退，这是必需的而非可选。** 前端路由是 history 模式，用户直接
打开或刷新 `/records` 这类路径时，服务端收到的是一个磁盘上并不存在的路径；不做处理时请求会
落到静态资源处理器抛出 `NoResourceFoundException`，再被兜底的 `GlobalExceptionHandler` 变成
500——单 jar 交付物一刷新就碎。`SpaWebConfig`（`WebMvcConfigurer`）注册 `/**` 并挂一个继承
`PathResourceResolver` 的解析器，找不到真实资源时回退到 `index.html`。

回退有两条硬边界：**只作用于非 `/api` 路径**（未知 API 路径的既有行为不变），**末段带扩展名的
不参与回退**（打错的 `.js`/`.css` 地址不变成 200 的 HTML）。没有打包前端时 classpath 下没有
`static/index.html`，回退退化为空操作，因此无需条件开关。注意 `GET /` 由 Boot 的
`WelcomePageHandlerMapping` 接管并转发到 `index.html`，优先级高于资源处理器。

一处取舍：单模块结构下 `target/classes` 同时喂 CLI jar 与 web jar，因此 `-Pfrontend` 时 CLI
jar 也会捎带一份 `static/`；默认构建不含。要彻底隔离得拆多模块，不值得。

### 第一阶段 API 与 DTO

| 接口 | 输入/输出 | 协议 |
|---|---|---|
| `GET /api/meta` | `MetaDto` | 版本由后端包元数据提供 |
| `GET /api/algorithms/search` | `AlgorithmDto[]` | 6 个代表搜索器 |
| `GET /api/algorithms/decoders` | `DecoderDto[]` | 8 个原生解码器 |
| `GET /api/instances` | `InstanceDtos.Summary[]` | 不暴露服务器路径 |
| `GET /api/instances/{id}` | `InstanceDtos.Detail` | ID 必须存在于后端白名单 |
| `POST /api/solve` | `SolveDtos.Request/Result` | 始终同步，预算严格互斥 |

| `POST /api/experiments/{id}/cancel` | `ExperimentTask` | 请求取消，保留已完成结果 |
| `POST /api/experiments/{id}/retry` | `ExperimentTask` | 只补算缺结果的格子 |

第二阶段增加 `/api/experiments` 任务资源：`preview` 校验任务笛卡尔积与预算规则，
创建端点返回 `202 Accepted`，后台工作池执行独立求解，`/{id}/events` 以 SSE 推送
进度快照，列表与详情端点提供真实运行记录。任务、进度、单格结果与事件序号都持久化到
受控目录，服务启动时自动恢复（见下节）。

#### 并发模型：固定两级线程池

调度层是一个 2 线程的 `dispatcher`（同时最多 2 个实验在跑），执行层是一个全局共享的
8 线程 `workers` 池；每个实验再用一个 `Semaphore` 把在飞的格子数卡在自己的
`parallelism` 上。这样做的原因是最初的「每个实验一个线程池」结构里，两层池相乘，
提交几个并行度 8 的实验就会开出远超 CPU 核数的线程，彼此抢 CPU 让每个任务的实际
预算都被拉长。现在线程总数有上界，实验之间只争信号量许可，不争线程创建。

提交与收集必须交错进行：先把全部格子提交再收集，会在许可耗尽时自锁（提交循环等许可、
许可只在收集循环里释放）。因此 `run` 循环用 `Semaphore.tryAcquire()`，拿不到许可就先去
收集一个已完成的任务再回头抢，收集走 `ExecutorCompletionService`。这里刻意不用手写的
阻塞队列：被取消而从未启动的任务不会投递任何完成通知，手写队列会让收集循环永久挂起，
而 `ExecutorCompletionService` 对取消的任务同样会给出一张完成票据。

#### 取消与重试

取消是协作式的：`future.cancel(true)` 只负责把中断标志打在运行中的工作线程上，真正
「停下来」由求解器自己在循环头部检查 `SearchLimit.cancelled()` 完成——一次评价可能长达
数十毫秒，只在任务边界检查会让取消按钮迟钝几秒到几分钟。被取消的格子走的是既有的
「返回当前历史最优解」路径，所以已经算出来的结果天然有效，取消不会丢弃它们。

重试只补缺口：结果按格子下标存进 `AtomicReferenceArray`，`retry` 重新提交时跳过已经有
结果的格子。为此失败的格子只累加失败计数、不写占位结果，否则重试会把失败当成已完成。
`Job` 上带一个 `epoch`，重试时自增；上一轮的收尾逻辑（清理在飞集合、推送终止事件、关闭
emitter）只有在 `epoch` 未变时才执行，避免旧线程把新一轮的进度流误判成已结束。

#### Web 实验任务的持久化

任务与结果落在 `packing.experiment-store`（默认 `results/web-experiments`）下，一个任务一个目录：

```text
<存储根>/<task-id>/meta.bin                请求、状态、时间戳、取消标记、事件序号
<存储根>/<task-id>/cells/<下标>.bin        单个格子的标量结果
<存储根>/<task-id>/cells/<下标>.layout.bin 同一格子的放置列表与收敛轨迹（伴生文件）
<存储根>/<task-id>/artifacts/              按需生成的 CSV / HTML / SVG 产物
```

每次写入都是「先写同目录临时文件，再原子替换」。断电或崩溃只会留下一个被忽略的
`.tmp`，绝不会让 `meta.bin` 变成半截文件——否则启动恢复连任务都读不出来。原子替换是这里
唯一的安全性来源，因为整个方案没有日志、没有事务，靠的就是「每个文件要么是旧的完整版本、
要么是新的完整版本」。

**为什么没有复用核心层的 `.experiment-checkpoint.bin`。** 那是本层最初的首选方案，
核对后确认有三处硬伤：

1. 它是**位置式**格式，写入与读取严格按字段顺序对应。Web 侧要补的恰好是状态机信息
   （任务状态、事件序号、取消标记），而往位置式格式里追加字段会让旧文件整体错位。
2. 它是**累积清单**：串行路径每完成一次运行就重写全部历史，并行路径为了维持与串行一致的
   顺序，还要等齐所有前序下标才追加。Web 侧是「收一个完成就落一个」，粒度与时机都对不上。
3. `RunCheckpoint` 是包级私有，Web 包无法访问，也没有公开的保存接口。

因此采用「一个任务一个目录、一个格子一个文件」的最小方案：每次结果到达只写几十字节的
单个文件，天然增量，不必触碰算法核心的任何代码，也不需要把核心的包私有类提权成公开 API。
代价是两套持久化并存。

**放置列表放在伴生文件里，而不是塞进 `cells/<下标>.bin`。** 结果有两部分：进统计的标量
（利用率、装入面积、耗时）和只用于回看的放置列表与收敛轨迹。后者体积是前者的几十倍，
而列表页、进度条、导出统计都只需要前者。把它们分开的直接收益是**旧的 `.bin` 格式与
读写契约一个字节都不用改**——恢复路径里已经跑通的那部分完全不动，新增的
`cells/<下标>.layout.bin` 缺失时只损失那一格的排样图。对应地，`isCellFile` 必须显式排除
`.layout.bin`，否则读标量时会把伴生文件按标量格式解析，得到一整屏垃圾数值：
位置式二进制格式里，多读一个字段的后果不是报错而是错位。

**产物按需生成，不进热路径。** `ExperimentArtifacts` 是核心层的既有能力，Web 层只在
用户显式点击时调用它，并把结果写进 `artifacts/`。生成顺序是「先在
`artifacts.building-<纳秒>` 里写全，再整体替换」，因此中途失败不会留下一份半截报告
覆盖掉上一次可用的产物。`ExperimentArtifacts.writeAll` 不产出
`experiment-metadata.properties`，而 `report.html` 里有一条指向它的链接，所以生成后要补写，
否则用户拿到的报告里躺着一条死链。

#### 重启恢复的状态转换

| 重启前状态 | 重启后 | 理由 |
|---|---|---|
| `RUNNING` | `CANCELLED` | 进程已消失，没有任何线程在推进它；继续标成运行中等于撒谎。**不自动续跑**：重启往往正是运维在干预，此时静默拉起重活是最不该做的事。用户看到「已取消 · 37/48」后按一次重试即可接着算。 |
| `QUEUED` | 自动重新排队 | 一个格子都没跑过，恢复它不存在「静默拉起」的问题，对用户完全透明。 |
| `COMPLETED` / `FAILED` / `CANCELLED` | 原样恢复 | 只恢复记录，不恢复执行。 |

有两个容易忽略的一致性细节：

- **优雅停机与进程被杀必须得到同一个结果。** 服务正常关闭时线程池被中断，任务会走到
  「被中断」的失败分支。如果不加处理，运维停一次服务就会把在跑的实验记成 `FAILED`——
  明明只是没跑完，却被报成执行失败。因此停机期间不再改写磁盘，保留 `RUNNING`，
  交由下次启动统一转成 `CANCELLED`：两条路径收敛到同一语义。
- **恢复出来的终态任务不重放 `complete` 事件。** 事件序号是从磁盘续上的，若在恢复时重放，
  一个带着旧序号的客户端重连会收到一条「序号比自己已知的还新」的重复终止事件。
  客户端若在任务结束后才连上来，订阅路径里「终态必发终止事件」那条会补一份快照，
  连接不会被挂住。

**事件序号必须跟着进度一起落盘**，而不是等到终态才写。进程若在中途被硬杀（不走
`@PreDestroy`），磁盘上会留下一个过期的序号；重启后新事件从旧序号之后开始，而一个拿着
更大 `Last-Event-ID` 的客户端会认为「这些都是我已经看过的」而全部丢弃，界面就永远停在
旧进度上。每次收集多写一次几十字节的元数据，换掉这个隐患是划算的。这一次写入放在中断
检查之后：被中断时再写一遍既留不住什么（`RUNNING` 重启后一律转成 `CANCELLED`），
又可能恰好停在「写了临时文件、还没替换」的中间，留下一个没人认领的残骸。

**同一个任务的元数据写入必须串行。** 元数据是一份「读-改-写」式的快照，而调用它的有
运行中的收集循环（推进进度）和 `cancel()` / `retry()`（改状态与取消标记）两方，
本来就会并发。两处约束缺一不可：

- `persist()` 自己持有任务锁。调用点里收集循环在锁外、取消与重试在锁内，若把加锁
  留给调用点，迟早会有一个新调用点忘记，而症状是状态被静默回退——最坏的是取消写入被
  收集写入覆盖，磁盘上的取消标记退回 `false`，重启后一个用户已经叫停的实验被重新排进队列。
- 暂存文件名必须每次唯一（`.tmp-<序号>`），不能按目标名拼一个固定的 `meta.bin.tmp`。
  共用固定名字时，后写者的 `newOutputStream` 会先把前写者正在写的文件截断，
  先 `move` 走的一方就让另一方撞上 `NoSuchFileException`。

停机本身也需要等待：`close()` 只 `shutdownNow()` 就返回是不够的，一个已经走到
「写临时文件 → 原子替换」的收集循环打断不了，必须等它把这一次写完。否则调用方会以为
服务已经停了，而存储目录仍在被写——测试里表现为临时目录删不掉，生产里表现为停机后
目录还在变动。

#### 存储目录的保留策略

`packing.experiment-store-max-tasks`（默认 200）限制保留的任务数，超出时删掉最旧的终态
任务。两条约束各自都能独立地搞坏东西：

- **只删终态。** 排队中与运行中的任务目录正在被写入，删它等于一边写一边拆房子；
  更何况它承载的是用户正在等的结果。宁可超限也不删。
- **候选只从保留窗口之后取**（`tasks.subList(上限, 末尾)`），而不是「删到不超限为止」。
  后者的症状很隐蔽：若最新的那批恰好是唯一的终态任务，被删的就会是刚跑完的那条记录——
  既没腾出该腾的空间，又丢了一条最新结果。上限为 0 或负数表示关闭保留策略。

清理必须发生在**恢复之后**，顺序反过来会把刚要恢复的任务当成「旧的」删掉，
用户重启一次丢一批记录。清理时还要一并移除内存中的任务条目，否则列表里会留下
一条指向已删目录的幽灵记录。

#### 产物的下载边界

下载端点 `GET /api/experiments/{id}/artifacts/{name}` 里，`name` **不是路径，是一把钥匙**：
只有命中服务端产物清单的名字才会被放行。校验分三层，顺序有讲究：

1. **先把控制字符挡掉再做任何路径操作。** `Path.of()` 遇到含 NUL 的名字会抛
   `InvalidPathException`，那是个 500 而不是 404，等于把「这个名字不合法」和
   「服务器炸了」混为一谈。
2. **分隔符黑名单只禁 `..`、`\\`、前导 `/`、绝对路径与控制字符，不禁 `..` 之外的斜杠。**
   产物清单本身就带嵌套目录（`convergence/gcut1.svg`），一刀切禁掉所有 `/` 会让
   一半产物不可下载。
3. **规范化后必须仍在产物根目录之内**（`file.startsWith(root)`），且确实是个普通文件。

三层任一不通过都报**同一个** `EXPERIMENT_ARTIFACT_NOT_FOUND`，与「文件不存在」不可区分——
否则这个端点就成了探测存储目录结构的工具。响应一律带
`Content-Disposition: attachment`：产物里既有 HTML 也有 SVG，内联渲染等于把用户实验目录
里的内容当成同源页面执行。

用 `/{*name}` 而不是 `/{name:.+}` 匹配路径：后者是单段通配，遇到带子目录的名字压根不匹配，
请求会掉进静态资源处理器抛 `NoResourceFoundException`；全局处理器现在会稳定映射为结构化 404，
但仍无法得到产物端点自己的错误码，因此下载路由必须使用 `{*name}` 捕获完整相对路径。
`{*name}` 捕获「剩余整段路径」且会多带一个前导斜杠，控制器先剥掉它再交给校验逻辑。

#### 分析视图的数据出口

`GET /api/experiments/{id}/analysis` 一次返回标量结果、逐格明细（含收敛轨迹）与实例几何，
供前端的热力图、排名、箱线图与收敛对比共用。之所以要单独开一个端点而不是让前端复用
`GET /{id}` 加 SSE：轨迹只存在伴生文件 `.layout.bin` 里，任务对象上本来就没有，
而四张图需要**同一时刻**的对齐数据——分开取会取到不同进度下的两份快照。

它与产物生成在终态要求上是**刻意相反**的：`POST /artifacts` 对运行中的任务报 409，
因为产物是一次成型的快照，半途生成会给出误导性的报告；分析视图则允许任务在跑，
缺的格子留空，因为图本来就是随结果陆续到达而更新的。

`cells[i]` 与 `results[i]` 逐位对齐，顺序是「实例 → 搜索器 → 解码器 → 种子」的笛卡尔积。
排名口径与核心报告统一为「同实例均值，并列同名次、之后跳号」，前端 `analysis/` 那层
复刻了同一套定义，避免页面上显示的名次和下载报告的 CSV 对不上。

单格轨迹超过 2000 点会被等距抽样并置 `curveTruncated`，**末点始终保留**：曲线的终点就是
这条轨迹的结论，被抽样规则顺手丢掉的话，图上最后一段会停在一个中途值上，看起来像「没跑到」。

#### SSE 断线重连

每条事件都分配单调递增的序号，并以 `id:` 字段下发；浏览器 `EventSource` 自动重连时会
通过 `Last-Event-ID` 请求头带回最后收到的序号，服务端据此补发断线期间的事件
（也可用 `?lastEventId=` 显式指定）。事件缓冲是容量有界的双端队列，超限时丢弃最旧的
事件但保留序号，因此「补发起点过旧」会表现为少补几条而不是序号错乱。订阅时无论是否
重连，只要任务已处于终态就补发一次进度快照加一个 `complete` 终止事件——否则「任务快得
来不及订阅」会让界面永远停在等待状态。心跳注释行定期下发，用来让中间的代理不要掐断
长时间没有业务事件的连接。

错误统一为 `ApiErrorDto`：`code`、`message`、`fieldErrors`、`requestId`、`timestamp`；
不返回 Java 堆栈。

### `model`

`Instance`、`Item`、`Placement` 和 `Solution` 是不可变记录，统一表示输入和输出。几何坐标以左下角为原点，SVG 生成时再转换为屏幕坐标。

### `solver`

`PackingAlgorithm` 是统一求解接口。构造式算法直接生成布局；Tabu、SA、ACO、ILS 和 GA 系列优化零件优先级排列，通过 `PackingDecoder` 生成坐标。默认使用 Skyline，也可注入 Shelf-BAF、Floor-Ceiling、两种 Bottom-Left、Skyline-BL-WM、MaxRects-BEST 或 Guillotine-BSSF-SAS-RM，从而将“如何搜索顺序”与“如何把顺序解码成布局”分离。

只有在 `ItemOrder.INPUT` 下严格遵守搜索优先级的引擎才会注册为解码器。Shelf-GLOBAL 会根据当前布局重新选件，因此保留为独立排样引擎，不伪装成会吞掉搜索顺序的解码器。

`PackingDecoder` 有两条路径：`solveInPriorityOrder` 返回完整 `Solution`，用于最终产出；
`packedAreaInPriorityOrder` 只返回装入面积，用于搜索过程中比较候选。后者默认退化为
「完整解码后取面积」，解码器可覆写以省去构造放置列表的开销。搜索阶段绝大多数候选只需要一个分数，
因此六个搜索算法默认走轻量路径。

`DecodingCache`（包级私有）是搜索层共用的「零件排列 → 装入面积」有界 LRU 记忆层，
被 Tabu、SA、ACO、ILS、GA 六个搜索算法共用，取代了它们各自重复实现、容量语义还不一致的私有缓存。
它**只存面积不存 `Solution`**：把携带整张放置列表的对象长期留在缓存里，等于钉住热路径上最大的一笔分配，
反而拖慢 GC。需要完整布局时走 `DecodingCache.solve`，不经过缓存。

缓存刻意**不内置计数器、不做预算判定**：是否把命中计入评价数、预算耗尽如何退出，
全部留在各算法原有循环里，因此各算法的评价计数口径与未加缓存时逐位一致。
需要说明的是，Tabu/SA 的候选由随机交换生成，几乎不可能重复，缓存对它们命中率接近零；
缓存的收益主要是消除了重复实现，真正的提速来自解码器内部的轻量评分路径与数据结构优化。

### `validation`

`SolutionValidator` 不复用求解器内部几何状态，独立验证输出，避免求解器与验证器共享同一错误。

### `experiment`

- `AlgorithmCatalog`：维护工程主入口和高级策略分层。
- `SolverFactory`：将稳定算法标识转换为具体求解器。
- `ExperimentRunner`：负责数据、种子、预算、预热和结果验证。支持按 `parallelism` 配置并行独立运行；
  任务清单按串行顺序编号、结果按下标回填，因此并行产出的运行列表与串行顺序和数值完全相同。
  时间预算实验强制串行（并行会让耗时不再公平）。
- `ExperimentArtifacts`：生成原始数据、汇总统计、排样图和报告。

## 扩展新算法

1. 实现 `PackingAlgorithm`。
2. 在 `AlgorithmId` 中增加稳定标识。
3. 在 `SolverFactory.create` 中注册构建逻辑。
4. 在 `AlgorithmCatalog` 中声明展示层级、家族和代表入口。
5. 增加几何不变式、边界情况、随机实例和工厂注册测试。
6. 确认实验结果通过 `SolutionValidator`。

单算法命令行的别名与自定义参数由 `CommandLineSolverFactory` 解析；未覆盖参数的算法最终仍委托给 `SolverFactory`。这样命令行和批量实验共享同一份核心算法注册，不在 `Main` 中重复维护构造分支。

仓库只保存源码、基准文本数据和工程文档。任务原件、教程、演示文稿及压缩资料不进入版本库，并由 `scripts/check-repository.sh` 和持续集成共同检查。

## 稳定性约定

- `AlgorithmId` 用于 CSV 和产物文件名，已发布标识不随意重命名。
- 随机算法仅使用配置中的随机种子。
- 搜索过程可接受劣解，最终返回值必须来自单独保存的历史最好解。
- 时间实验必须预热；质量对比必须同时报告合法性和实际评价数。
