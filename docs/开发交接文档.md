## 6. 尚未完成与已知边界

### 6.1 实验任务持久化（已完成，仍可加强）

已完成跨进程恢复：

- 每个任务在受控目录下有自己的 `meta.bin`（请求、状态、时间戳、事件序号）与
  `cells/<下标>.bin`（单格结果），写入一律「临时文件 + 原子替换」。
- 启动时扫描存储根目录恢复任务、进度与明细，未完成的任务可以接着算。
- 存储根目录由 `packing.experiment-store` 配置，客户端无法指定。
- 事件序号随进度一起落盘，跨重启继续递增。

**没有复用核心层的 `.experiment-checkpoint.bin`**，原因见 `docs/架构说明.md`
「Web 实验任务的持久化」，主要是位置式累积清单格式与 Web 的「单格增量落盘」语义不匹配，
且 `RunCheckpoint` 是包级私有。核心层与 Web 层各自保持自己的持久化，互不侵入。

仍存边界：

- 未复用核心 `ExperimentArtifacts`，因此还没有 CSV/HTML/SVG 产物与下载 API。
- 没有保留策略：任务目录只增不删，长期运行需要手工清理或加一个上限。
- 「暂停」仍无对应语义：只有「取消（保留结果）」与「重试（补缺口）」两个动作。

本轮修掉的三处并发与停机缺陷（此前没有测试能发现）：

- 同一任务的元数据有两个写者（收集循环推进进度、`cancel()`/`retry()` 改状态），
  并发进入 `saveMeta`。暂存文件名原本是固定的 `meta.bin.tmp`，后写者会把前写者正在写的
  文件截断，先 `move` 走的一方让另一方撞上 `NoSuchFileException`；更坏的情况是取消写入
  覆盖终态写入，磁盘上留下过期状态。现在暂存文件名每次唯一，`persist()` 自己持有任务锁。
- `close()` 只 `shutdownNow()` 不等待，已经进入原子替换的收集循环打断不了，
  于是「以为服务已停、存储仍在被写」。现在会在上限内等待线程池终止，优雅停机与进程被杀
  在恢复语义上继续收敛到同一结果。
- 收集循环里那次「序号跟着进度落盘」的写入移到了中断检查之后，避免被中断时在
  「写了临时文件、还没替换」的中间留下残骸。

### 6.2 并发模型（已收敛，仍可加强）

已完成的收敛：

- 调度层为固定 2 线程 dispatcher，执行层为全局共享 8 线程 workers 池，
  每个实验用 `Semaphore` 卡自己的并行度，线程总数不再随实验数相乘。
- 结果按完成顺序回收（`ExecutorCompletionService`），进度不再被提交顺序靠前的慢格子挡住。

仍存边界：

- 许可上限 `parallelism` 与工作池线程数是两个独立常量（8 与 8），若未来放开并行度上限，
  需要同步调整工作池大小，否则许可会多于实际能同时开跑的线程。
- `currentTask` 是并行工作线程最后写入的提示值，仅用于展示，不应当作严格调度状态。
- 没有队列容量与拒绝策略：任务总量上限靠 500 个格子的矩阵上限间接兜住。

### 6.3 SSE 边界（已补齐，仍可加强）

已完成：

- 事件带单调序号与 `event:` 名，支持 `Last-Event-ID` 头与 `?lastEventId=` 参数补发。
- 终态任务被订阅时补发进度快照加 `complete`，覆盖「任务快到来不及订阅」。
- 心跳注释行定期下发，避免中间代理掐断空闲连接。
- MockMvc 已覆盖流式响应的事件名、序号与重连收尾。

仍存边界：

- 事件缓冲有界（600 条），断线过久会丢最旧事件；补发是「少补几条」而非「序号错乱」，
  但前端此时只能拿到进度快照，无法逐条回放。
- 没有服务端主动 ping 的存活探测，重连上限 5 次后前端放弃，需要用户手动刷新页面。

### 6.4 记录与产物

- 记录页进入时读取一次，停留页面时不会持续刷新其他任务。
- 尚未提供 CSV、HTML、SVG 或 checkpoint 下载 API；方案与落点清单见第 8 节。

### 8.1 关键结论：布局数据走伴生文件持久化

生成排样 SVG 与收敛图需要每个格子的 `placements` 与 `convergence`，而当前
`ExperimentTaskService.ServiceCellSolver.solve`（约 L515）把这两样**丢弃**了，只留标量存进
`ExperimentDtos.ResultRow`。所以第一件事是让单格结果把布局数据带回来。

选定方案：每格在现有标量 `.bin` **之外**再落一份**伴生文件**。**现有 `.bin` 格式与读写契约
完全不动**——`ExperimentTaskStoreTest` 把「写入端与读取端逐字段对称」钉得很死，往位置式格式里
加字段会牵动整条读写链。

```text
<task-id>/
  meta.bin                    现状不变
  cells/<下标>.bin            现状不变：标量指标
  cells/<下标>.layout.bin     新增：placements + convergence（伴生）
```

约定：

- 伴生文件**缺席时**，该任务只是「暂不可下载产物」，**读取与恢复照常**；旧任务目录不受影响。
- 写入沿用现有 `temporaryPath` + 原子替换，与 `.bin` 同一套机制。
- 需要新增 `ExperimentTaskStore.saveLayout` / `loadLayouts`。
- **必须收紧 `isCellFile` 的过滤**：它现在只排 `.bin` 与 `.tmp`，`.` 的匹配会把
  `<下标>.layout.bin` 当成 `cells/<下标>.bin` 读进来，导致格子结果被污染。过滤要显式排除 `.layout.bin`。
- 伴生文件属「可选产物输入」，不进 `VERSION` 的语义校验；文档说明它**可被安全删除**
  （删了只是不能下载产物），这样保留策略（8.2 第 3 条）可以先删它再删整个目录。

### 8.5 本轮落地结果与对方案的偏差

按 8.1–8.4 全部落地，后端测试 220 → 246、前端 13 → 42，另加 1 条端到端冒烟。
以下是执行过程中与本节方案有出入的地方，以及新发现的边界。

**一处方案增补：产物清单要用 `POST` 触发。** 8.2 写的是「新增 `GET /{id}/artifacts`（清单 JSON）
与 `GET /{id}/artifacts/{name}`（下载）」，但生成产物**会写磁盘**，挂在 `GET` 上的话，浏览器、
代理和预取都可能替用户发请求，表现为「看一眼清单就触发一次全量重写」。最终拆成
`GET`（只读清单）与 `POST`（生成后返回清单）。下载端点仍按原方案是 `GET`。

**一处实现细节：路径变量必须是 `{*name}` 而不是 `{name:.+}`。** 8.2 原样的 `{name:.+}` 是
**单段**通配，`convergence/gcut1.svg` 这类带子目录的名字压根不匹配——请求会掉进静态资源
处理器抛 `NoResourceFoundException`，最终变成一个莫名其妙的 500，而不是我们的错误码。
真实实验的产物里 `layouts/<实例>/<算法>.svg` 是二层嵌套，这个坑一定会踩到。
改用 `{*name}` 捕获「剩余整段路径」，注意它会多带一个前导斜杠，控制器要先剥掉。

**一处发现，本轮未改：未知路径统一返回 500。** `GlobalExceptionHandler` 没有
`NoResourceFoundException` 的处理器，于是它落进兜底的 `@ExceptionHandler(Exception.class)`，
被当成 500 `INTERNAL_ERROR`。实测 `/api/nonsense`、`/totally/unknown` 一律 500。
这**不是产物端点引入的**，是既有的全局行为。8.2 明确写了「无需改 `GlobalExceptionHandler`」，
故本轮不动；若要收口，加一个返回 404 的处理器即可，但它会改变所有未知路径的响应码，
属于独立决定。

**一处测试写法上的坑：MockMvc 不做路径规范化。** 真实 Tomcat 会在路由前把 URL 里的 `../`
折掉（`artifacts/../runs.csv` → `/api/experiments/runs.csv`，于是没有路由匹配）；
MockMvc 直接按原样匹配，同一个请求会打到控制器并返回 404。因此「越界拒绝」的断言要用
`--path-as-is`（curl）或直接给带 `..` 的名字，别指望容器替你规范化——
用容器行为当断言，测的就是容器而不是自己的代码了。

**一处需要复核的操作事故：** `frontend/src/composables/useSolveForm.test.ts` 是被**整个重写**
的（原有 5 个用例，重写后 9 个），重写前没有先读原文件。该文件此前未纳入 git（`frontend/` 整体
未跟踪），也没有缓存副本，**原文不可恢复**。新用例覆盖了同一组行为（预算二选一、上下界校验、
复位、`buildRequest` 活性），但无法保证是原用例的超集。若原文件里有本仓库不关心的断言，
需要重新补。

**一处按要求未做：磁盘写满（ENOSPC）下的降级语义。** 8.3 已明确记为不做，本轮保持不做，
只保证只读目录下的行为（非 root 时用权限位造，root 下 `assumeFalse` 跳过）。

### 8.6 分析视图与记录页（P2 第 4、5 项）

第 4 项（热力图 / 排名 / 箱线图 / 收敛对比）落在**前端交互分析页**，不是核心 `report.html`；
第 5 项（记录页筛选 / 排序 / 实时更新）与之同批完成。

**为什么必须新开一个后端端点。** 四张图都要逐格收敛轨迹，而轨迹只存在伴生文件
`cells/<下标>.layout.bin` 里，`GET /{id}` 与 SSE 推的任务对象上根本没有。更重要的是：
四张图需要**同一时刻**对齐的数据，分别去取会取到不同进度下的两份快照，图上出现自相矛盾。
于是新增 `GET /api/experiments/{id}/analysis`，一次返回 `results` + `cells`（含轨迹）+
`instances`（板材尺寸与零件数，做轴标签）。

**它与产物生成在终态要求上刻意相反。** `POST /artifacts` 对运行中的任务报 409（产物是一次
成型的快照，半途生成会给出误导性报告）；`/analysis` 允许任务在跑，缺的格子留空。
测试 `analysisIsAvailableWhileTheExperimentIsStillRunning` 与
`refusesToGenerateWhileTheExperimentIsStillRunning` 各守一端，改动任何一边都会红。

**长轨迹抽样，末点必须保留。** 单格轨迹是「每代一个点」，20 万次评价能攒十几万个点，
原样塞进 JSON 是几十 MB。超过 2000 点等距抽样并置 `curveTruncated`，**末点始终保留**——
曲线的终点就是这条轨迹的结论。前端在图下标明「已抽样」，否则用户会以为算法真的只迭代了
图上那么多次。`analysisDownsamplesLongTracesButKeepsTheLastPoint` 钉死这两点。

**排名口径必须与核心报告一致。** `frontend/src/analysis/experimentAnalysis.ts` 复刻了核心的
「同实例均值排名，并列同名次、之后跳号」定义。若前端另起一套，页面上显示的名次会和用户
下载的 CSV 对不上，而这类不一致几乎没人会去核对。对应的测试在
`experimentAnalysis.test.ts` 里连并列跳号（1、1、3）都单独钉了一条。

**前端四张图各自最容易骗人的地方**（测试逐条覆盖）：
缺数据渲染成破折号而非 0%（热力图）；归一化用所有系列的并集而非各自归一，否则宽窄不同的
两行看起来一样宽（箱线图）；用阶梯线而非折线，否则会在两次改进之间画出一条并不存在的
「逐渐变好」，且颜色按算法名哈希固定，系列增减时其余线不改色（收敛对比）。

**本轮修掉的一个真实缺陷。** `RecordsView` 的注释承诺「全部结束就自动停」，但轮询回调从不
重新评估 `running`，定时器会一直空转，页面上明明没有活干却每 3 秒发一次请求。
`RecordsView.test.ts` 的「有任务在跑时自动轮询，全部结束后停止」抓到了它，已修。
写这条测试时踩过一个坑：替身若复用同一个数组对象，Vue 会因为引用没变而不重算派生状态，
测出来的行为与线上不一致——替身要像真 API 一样每次返回新数组。

**本轮修掉的一个真实模板错误。** `AnalysisView.vue` 里一个 `<header>` 被写成 `</article>`
闭合。此前该文件没有任何测试导入它，`vue-tsc --noEmit` 的输出又被 `tail` 截断，因此一直
没被发现——直到为它写测试时 Vitest 编译模板才报出来。教训：给视图补测试不只是覆盖率，

## 10. 本轮主线（P3）的执行记录

P3 两项都已落地：**部署形态**（单 jar 可选打包）与 **CI 构建步骤**。

### 10.1 部署形态：单 jar 可选打包

目标形态经确认是「**单 jar 可选打包**」：默认 `./mvnw clean verify` 一分不变、不触碰 Node、
保留独立前端部署；需要自带前端的可执行包时显式启用 `frontend` profile：

```bash
./mvnw -Pfrontend package
java -jar target/rectangle-packing-1.0.0-web.jar   # http://localhost:8080 即前端
```

做法（`pom.xml` 的 `<profile><id>frontend</id>`，照 `bench` profile 的风格与注释写）：

- `frontend-maven-plugin` 在 `generate-resources` 阶段下载固定版本的 Node（`v20.19.0`）与
  pnpm（`10.4.1`）到 `target/`，再复用 `frontend/package.json` 里已有的脚本执行
  `pnpm install --frozen-lockfile` 与 `pnpm build`。**构建机不需要预装 Node**，本机（无系统
  node）与 CI 因此共用同一条路径。
- `maven-resources-plugin` 把 `frontend/dist` 复制到 `target/classes/static`
  （`process-resources` 阶段，晚于前端构建），Boot 作为 classpath 静态资源托管。

**为什么用 profile 而不是让默认构建带上前端。** 默认构建带上前端，会让每个只想跑后端测试的
场景都被迫具备 Node 工具链与前端依赖，后端 `verify` 变慢也更脆。profile 让「交付单 jar」成为
一个显式动作，两者互不干扰。

**一处已知取舍：`-Pfrontend` 时 CLI jar 也会捎带一份 `static/`。** 单模块结构下
`target/classes` 同时喂 CLI jar 与 web jar，两个 jar 共享同一棵 classpath 资源。要彻底隔离
得把项目拆成多模块，为一个「CLI jar 里多几十 KB 静态资源」的问题不值得。默认构建不含它。

### 10.2 SPA 回退：单 jar 形态的硬需求

前端路由是 `createWebHistory()`（history 模式），用户直接打开或刷新 `/records` 这类路径时，
服务端拿到的是一个磁盘上不存在的路径。**不做处理的话单 jar 一刷新就碎**：
`GlobalExceptionHandler` 没有 `NoResourceFoundException` 处理器（见 8.5），请求落到静态资源
处理器后抛出该异常，被兜底的 `@ExceptionHandler(Exception.class)` 变成 500。

新增 `src/main/java/com/assessment/packing/web/config/SpaWebConfig.java`（`WebMvcConfigurer`）：
注册 `/**` → `classpath:/static/`，挂一个继承 `PathResourceResolver` 的解析器，找不到真实资源时
回退到 `index.html`。

**回退严格限定在非 `/api` 路径，且末段带扩展名的不回退。** 前者保证 `/api/nonsense` 的行为
一个字节不变（仍是兜底的 500），后者避免把打错的 `.js`/`.css` 地址变成 200 的 HTML 页面。
没有打包前端时 classpath 下没有 `static/index.html`，回退退化为空操作，因此无需条件开关。

三处实现细节值得留痕：

- **继承 `PathResourceResolver` 而不是直接实现 `ResourceResolver`。** 链尾是否会自动追加一个
  `PathResourceResolver` 取决于 webjars 等开关（Spring 的 `ResourceChainRegistration`
  只在 `isHasWebJars()` 为真时才追加），依赖它等于依赖一个自己控制不到的不变量。继承之后
  「按真实路径解析」始终由本类完成。
- **configurer 用 `@Order(HIGHEST_PRECEDENCE)` 先注册 `/**`。** Spring Boot 的
  `WebMvcAutoConfigurationAdapter` 默认也注册 `/**`，其私有 helper 会先查
  `registry.hasMappingForPattern(pattern)`，发现已有映射就跳过自己那条。因此行为确定，
  不依赖两个 configurer 的未知执行顺序。
- **`GET /` 由 Boot 的 `WelcomePageHandlerMapping` 接管，优先级高于资源处理器。** 它把 `/`
  转发到 `index.html`（真实容器里转发会执行，MockMvc 不执行）。测试因此断言
  `forwardedUrl("index.html")` 而不是响应体——这是 MockMvc 与容器的差异，不是实现问题。

### 10.3 CI 构建步骤

`.github/workflows/ci.yml` 在既有 `test` job 之外新增两个并行 job：

- `frontend`：`pnpm/action-setup@v4`（10）→ `actions/setup-node@v4`（22，缓存
  `frontend/pnpm-lock.yaml`）→ `pnpm install --frozen-lockfile` → `pnpm check` → `pnpm build`。
- `web-jar`：`./mvnw -Pfrontend -DskipTests package`，再 `unzip -l` 断言 web jar 里含
  `static/index.html` 与 `static/assets/`。**这是单 jar 路径在 CI 里唯一的长期看门人**——
  本地构建过一次不代表下次仍然能打出来。

**pnpm 必须先于 setup-node 安装**：setup-node 的 pnpm 缓存需要 pnpm 已在 PATH 上，顺序反了会
在 setup-node 这一步报「pnpm 未找到」。

**端到端不纳入 CI**（经确认）：Playwright 冒烟要真实后端与 Chromium，跑起来既慢又脆，
它的价值是本地手工守接缝，不适合当门禁。这与第 8.4 节「e2e 不进 `pnpm check`」是同一判断。
